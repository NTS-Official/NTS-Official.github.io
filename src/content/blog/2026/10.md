<p>上一篇写的是 wgpu-mc-neo（Neolectrum）那边的事。它没停 —— 11 月 1 日还有提交 —— 但重心确实慢下来了。这个月的绝大部分时间，我在另一个项目里。</p>

<p>那个项目叫 <strong>DXRMC / Illusion</strong>：把 Minecraft 的渲染后端整个换成 D3D12，然后在这个后端上做光线追踪和混合路径追踪。这篇先讲它是怎么搭起来的，以及第一周卡在什么地方。</p>

<h3>先说它是什么</h3>
<p>Minecraft 26.2 把渲染器抽成了可插拔后端的形状，Illusion 就是实现了那套接口的一个后端。分工大致是：</p>
<ul>
  <li><strong>MCDR</strong> —— C++ 侧。D3D12 设备、管线、着色器编译、光追与降噪都在这里，主设备文件现在是 10,694 行。</li>
  <li><strong>Illusion</strong> —— Kotlin / Java 侧。接在游戏里，管配置、管界面、把渲染任务递到 native。</li>
</ul>
<p>两边之间是<strong>纯 C ABI 动态库 + Java 25 的 FFM</strong>，126 个导出函数，一条 <code>Linker.nativeLinker()</code>。整个仓库里 JNI 的 <code>native</code> 声明数量是 0 —— 设计稿里写的"115 个 static native 加 2158 行 JNI 桥"已经是上一代的事了。</p>

<h3>路线图是十月中定下来的</h3>
<p>把顺序定成一条线：TAA → DLAA / DLSS → Mesh → VRS tier 2 → DLSSG（帧生成）→ Shaderpack。</p>
<p>理由很实际 —— 光追之前得先把"能跑"这件事做扎实，而抗锯齿、升频、几何这些恰好也是光追要吃的基础设施。先做它们，后面不至于返工。</p>

<h3>第一个障碍：入场时整屏冻结</h3>
<p>现象很朴素：启动加载界面的进度条不动；点进世界、"加载世界中"弹出的那一瞬间帧时间骤增。</p>
<p>根因是 DXC 编译加 D3D12 管线创建<strong>全部串行在主线程上</strong>，而且每一轮启动都重新编译一遍。主线程被占住就不产生新帧，不 present，屏幕定格在上一帧。</p>
<p>证据里最显眼的是两条 <code>P100 blit</code> 日志之间<strong>空了 8149.4 毫秒</strong>，那段时间主线程干了 92 次 <code>createGraphicsPipeline</code>、184 次 <code>compileHlslToDxil</code>。单次编译只要 5 到 25 毫秒 —— 慢在次数，不在单点。</p>
<p>于是给 <code>compileHlslToDxil</code> 加了 <strong>DXIL 磁盘缓存</strong>：键是 FNV-1a 64 位的（dxcompiler.dll 大小加时间戳、profile、entry、HLSL 源码），换了 dxcompiler 就整批失效；默认放在 <code>MCDR.dll</code> 同目录下的 <code>MCDR_dxil_cache\</code>。</p>
<p>不过缓存只消掉了 HLSL 到 DXIL 那一段。108 次 PSO 创建本身仍然在主线程上 —— 这件事到现在也没彻底解决，只是变得能忍受了。</p>

<h3>然后是 DLSS</h3>
<p>10 月 16 日把 DLSS 的基本实现接上去。接之前得先把 TAA 的 jitter 处理对，因为升频用的就是同一套抖动序列。</p>
<p>顺便说一句，这套东西真正的优势不在帧率。计划文档里写得很直白："换 API 能提升光追性能"这个假设<strong>已经被否证</strong>了，GPU 侧的瓶颈不因 API 改变。继续走 D3D12 的理由是实验价值、平台整合，以及 <strong>PIX</strong> 的 GPU 时间线。</p>
